# خطة اختبارات سلامة البيانات وإعادة الإنتاج

- الفرع: `audit/kpi-evidence-matrix-2026-11`
- النطاق: خطة تنفيذ واختبارات مقترحة مستندة إلى مراجعة `analysis/04_data_quality.py` و`analysis/10_export_dashboard_data.py` و`executive_dashboard/build_all.py` و`command_center/tests/test_command_center.py`.
- لا تغيّر هذه الوثيقة بيانات المصدر أو منطق الحساب أو المخرجات المنشورة.

## 1. ما هو موجود بالفعل

| المنطقة | الموجود | ما لا يثبته وحده |
|---|---|---|
| جودة معاملات المبيعات | `analysis/04_data_quality.py` يحسب عدد السجلات والفواتير، حدود التواريخ، التواريخ غير القابلة للقراءة، النواقص، تكرارات محتملة، السطور الصفرية/السالبة، فروق السطر والفاتورة، القيم الشاذة، وعدد الفواتير الشهري. | هو تقرير تشخيصي؛ لم يظهر اختبار مستقل يضمن أن كل شرط فشل عند تجاوز حد رقابي، أو أن المخرجات لم تتغير دون تفسير. |
| تصدير بيانات اللوحة | `analysis/10_export_dashboard_data.py` يجمع JSON/CSV في `dashboards/data.js` ويحوّل NaN/Infinity إلى null. | لا توجد في الملف نفسه مطابقة عامة لعدد الصفوف والمجاميع وبصمة المصدر بعد التصدير. |
| بناء لوحة الموبايل | `executive_dashboard/build_all.py` يوضح سلسلة البناء ويدعم `--check` و`--strict`، مع فصل لقطة سطح المكتب التاريخية عن سلسلة الموبايل. | يلزم توثيق/اختبار عدم الكتابة فوق الملفات الأصلية، وإثبات ثبات المخرجات عند تكرار البناء على نفس المدخلات. |
| مركز القيادة | `command_center/tests/test_command_center.py` يختبر نجاح checks، إجمالي المبيعات مقابل EDA، الشهر المفقود، ترتيب الفترات، AR الجزئي، هامش الوصفة، اكتمال الصفحات وتشغيل المتصفح. | هذه الاختبارات تخص command_center؛ لا تعتبر بديلًا عن مطابقة ملفات executive_dashboard أو dashboards/data.js. |
| بيانات القوائم المالية | `executive_dashboard/tests/test_statements.py` يختبر توازن الميزانية، مراجع أرقام ديسمبر، قائمة الدخل، مطابقة التدفق النقدي، وبعض النسب. | بعض النسب مثل DSO/DPO تحتاج اختبار معادلة مستقلًا؛ اختبار النطاق وحده غير كافٍ. |

## 2. مصفوفة ضوابط سلامة البيانات

| الرمز | الضابط | الاختبار المطلوب | معيار النجاح |
|---|---|---|---|
| DQ-01 | ثبات عدد السجلات | تسجيل row_count لكل ملف خام ومعالج ولكل مرحلة تحويل. | لا فرق غير مفسر؛ كل حذف/استبعاد له سبب وعدد معروف. |
| DQ-02 | عدم مضاعفة السجلات | كشف التكرار بمفتاح العمل المناسب، ثم فحص joins قبل/بعد. | لا تضاعف في عدد السطور أو المجاميع بسبب join؛ التكرار المحتمل لا يحذف تلقائيًا. |
| DQ-03 | مطابقة الفاتورة | مجموع line_total لكل فاتورة مقابل invoice_reported_total. | فرق ≤ حد العمل المعتمد؛ كل استثناء في تقرير قابل للتتبع. |
| DQ-04 | مطابقة المبيعات | مجموع المبيعات والكميات حسب الشهر والمصدر والعلامة التجارية مقابل المصدر/EDA. | تطابق ضمن tolerance موثق، مع فصل المرتجعات والخصومات. |
| DQ-05 | سلامة التواريخ | فحص parse failures، نطاق التاريخ، الترتيب، والفترات المفقودة. | لا تواريخ غير قابلة للقراءة بلا استثناء موثق؛ لا سد تلقائي لفترة ناقصة. |
| DQ-06 | اكتمال الحقول | قياس null/blank لكل حقل حرج حسب المصدر والفترة. | الحدود حسب الحقل؛ الحقول الحرجة لا تُملأ بصفر أو قيمة تقديرية تلقائيًا. |
| DQ-07 | مطابقة المخزون | عدد الأصناف والكميات والقيمة لكل جرد، خامات + تام، ومقارنة التغيرات بين الجرود. | الإجماليات تتطابق مع كشف الجرد؛ كل تغير/صنف مفقود موثق. |
| DQ-08 | مطابقة العملاء والموردين | أرصدة افتتاحية + حركات = أرصدة ختامية، حسب العميل/المورد والتاريخ. | فرق صفر أو ضمن tolerance موثق؛ اللقطات الجزئية تبقى جزئية. |
| DQ-09 | القوائم المالية | توازن الميزانية، معادلات قائمة الدخل، تغير النقدية، واتساق الفترات. | كل معادلة تتطابق ضمن حدودها؛ لا تُسوّى الفروق غير المفسرة بصمت. |
| DQ-10 | المصدر إلى التصدير | مقارنة كل جدول تصدير بمخرجات الدالة المصدرية، بالصفوف والمفاتيح والمجاميع. | تطابق كامل للمفاتيح والصفوف والقيم بعد قواعد التقريب المعلنة. |
| DQ-11 | قابلية إعادة الإنتاج | بناء المخرجات مرتين على نفس المدخلات في بيئة نظيفة ومقارنة SHA-256. | نفس المدخلات والإعدادات تنتج نفس المخرجات، أو فرق معروف ومفسر. |
| DQ-12 | عدم فقد البيانات الأصلية | مقارنة قائمة الملفات الخام وبصماتها قبل/بعد البناء. | لا تعديل/حذف/إعادة تسمية لأي مصدر خام خلال البناء. |
| DQ-13 | حداثة البيانات | ربط كل مجموعة بيانات بتاريخ المصدر وآخر تحديث وتاريخ التصدير. | تاريخ كل بطاقة/جدول لا يتجاوز تاريخ مصدره ولا يخفي قدم البيانات. |
| DQ-14 | الفلاتر والفترات | اختبارات قبل/بعد الفلترة حسب الشهر والمندوب والعلامة التجارية. | الفلتر لا يغيّر المجاميع خارج نطاقه، ولا يسرّب بيانات من فترة أخرى. |

## 3. ترتيب التنفيذ المقترح

### المرحلة 1 — خط أساس غير تعديلي
1. جرد الملفات الخام والمعالجة والمخرجات المنشورة على مستوى المسار والحجم وSHA-256.
2. حفظ أعداد السجلات والمجاميع الحالية لكل ملف رئيسي.
3. تسجيل تاريخ البيانات وأحدث فترة متاحة لكل مصدر.
4. لا يُعاد بناء أي ملف منشور في هذه المرحلة.

### المرحلة 2 — اختبارات التحويلات
1. إضافة اختبارات قبل/بعد لكل تحويل رئيسي في خط المبيعات.
2. اختبار مفاتيح الربط وعدد الصفوف قبل وبعد joins.
3. اختبار معادلات سطر الفاتورة وإجمالي الفاتورة والمجاميع الشهرية.
4. إبقاء سجلات التكرار المرشحة للمراجعة؛ لا حذف تلقائي.

### المرحلة 3 — اختبارات القوائم والمخزون والذمم
1. مطابقة كل ميزانية معادلةً ومرجعًا.
2. مطابقة قائمة الدخل لكل شهر مع الملف الأصلي.
3. مطابقة حركة المخزون والكميات والقيم بين كل جردين.
4. مطابقة أرصدة العملاء والموردين مع التقارير المطبوعة، وتحديد اللقطات الجزئية والمفقودة.

### المرحلة 4 — اختبارات التصدير والبناء
1. مقارنة كل export table مع دالة المصدر: count + key set + totals + null counts.
2. بناء مخرجات مؤقتة في مجلد اختبار، لا فوق الملفات المعتمدة.
3. مقارنة الناتج بالمخرجات الحالية مع بيان الفروق.
4. تشغيل `build_all.py --check` بعد التأكد من أن وضع check لا يغيّر ملفات المصدر/المخرجات خارج المقصود.
5. توثيق SHA-256 للمدخلات والمخرجات ونسخة الكود.

### المرحلة 5 — بوابة إصدار
لا يُسمح بتعديل واجهة أو نشر نسخة جديدة إلا بعد:
- اجتياز الاختبارات الحرجة.
- تفسير كل فرق في الصفوف أو المجاميع.
- عدم تغير أي مصدر خام.
- نجاح مطابقة الجداول المصدرة مع قيم المصدر.
- توثيق البيانات الناقصة والافتراضات وتاريخ البيانات.
- مراجعة النتائج على فرع مستقل دون دمج تلقائي.

## 4. اختبارات ذات أولوية عالية

1. **اختبار التصدير العام:** لكل جدول، تحقق من ID ثابت، مفاتيح فريدة عند اللزوم، عدد الصفوف، ومجاميع الأعمدة المالية/الكمية.
2. **اختبار عدم المضاعفة:** اختبر joins التي تربط الفواتير بالأصناف والعملاء والعلامات التجارية والوصفات.
3. **اختبار الفترات الناقصة:** تأكد أن الشهر الغائب يظل null/«يحتاج بيانات» ولا يحمل من الشهر السابق.
4. **اختبار AR الجزئي:** تأكد أن التقارير الناقصة لا تدخل في إجمالي كامل أو تُستكمل بالتخمين.
5. **اختبار المخزون:** مطابقة خامات + تام لكل تاريخ جرد مع التقرير المطبوع.
6. **اختبار إعادة البناء:** قارن ناتج بناء مؤقت مع النسخة المعتمدة دون الكتابة فوقها.
7. **اختبار البصمات:** أي اختلاف SHA-256 في مصدر خام يوقف بوابة الاختبار ويطلب مراجعة.

## 5. شروط التنفيذ الآمن

- جميع الاختبارات الجديدة والتعديلات على فرع مستقل.
- لا حذف أو تعديل لملفات `data/raw/` أو المستندات الأصلية.
- لا تشغيل بناء قد يكتب فوق نسخة منشورة قبل فحص أوضاع الكتابة ومسارات الإخراج.
- لا تعديل لـ `main` ولا نشر ولا دمج.
- لا تُحوّل تحذير جودة إلى حذف بيانات تلقائي.
- أي tolerance يجب أن يذكر بالعملة/الوحدة، والسبب، ومستوى التقريب.
- أي نتيجة «نجاح» يجب أن تستند إلى CI مكتمل ونتائج اختبار قابلة للفحص.

## 6. حدود الوثيقة

هذه خطة ضوابط مستندة إلى قراءة ملفات المصدر والاختبارات الموجودة، وليست تقرير تنفيذ. لم تُشغّل هنا إعادة بناء شاملة أو مقارنة فعلية لجميع ملفات البيانات الخام والمعالجة. يلزم تنفيذ كل اختبار على نسخة مؤقتة مع الاحتفاظ ببصمات ومخرجات المقارنة قبل اعتماد أي تغيير.
